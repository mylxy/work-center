# Email Skill Implementation Design

This document records the implementation design accepted for the local skill. GitHub Issues remain the repository's authoritative location for tracked product specifications.

## Problem

The user wants Codex to read and send Alibaba Mail without routine webmail login. This repository delivers only the reusable email skill; scheduling, weekly-report analysis, Bear journal aggregation, and durable Markdown summaries belong to a separate Calling Project.

## Package

- Create an explicit-only `$email` skill under `skills/email`.
- Bundle a Python 3.12 standard-library CLI at `scripts/mailctl`; do not require a daemon, MCP server, global command, virtual environment, or runtime package download.
- Install the skill with the repository's symlink pattern and keep the repository copy authoritative.
- Use IMAP over TLS on port 993 and SMTP over TLS on port 465. The first version has one `default` Mailbox Account and fixes `From` to that account.
- Store the third-party client security password only in macOS Keychain. Never accept it through arguments, environment variables, config files, prompts, or output.
- Run `auth setup` in one reusable PTY and attach that exact session to the visible integrated terminal. Before requesting password input, verify that the visible terminal contains the full command and Keychain password prompt. If attachment or session lifetime fails, provide the absolute command for the user to run manually instead of reporting that the hidden process is waiting.

## Calling Project boundary

- The Calling Project is exactly the process working directory. The CLI never searches parent directories or writes outside it.
- `mailctl init` creates `.mailctl/config.toml`, `drafts/`, `attachments/`, and `tmp/`, with user-only permissions and internal Git-ignore protection.
- Every generated file lives below `.mailctl/`. The CLI refuses to use tracked `.mailctl` state.
- No general audit log is maintained.

## Public CLI seam

The first version exposes only:

```text
mailctl init
mailctl auth setup
mailctl doctor
mailctl search
mailctl get
mailctl attachment get
mailctl prepare
mailctl draft show
mailctl send
```

Commands return structured JSON. Search supports exact sender/recipient addresses, start/end time, folder, subject text, Message-ID, attachment presence, and cursor pagination. It defaults to `INBOX`, 50 messages per page, and permits at most 200. Search results contain folder, UIDVALIDITY, UID, Message-ID, received time, sender, recipients, subject, snippet, and attachment presence; `get` returns detailed attachment metadata. The caller owns scan windows and deduplication.

`get` uses a stable message reference and fetches without setting `\\Seen`. It returns normalized plain text, optional sanitized HTML, collapsed quoted-history/signature indications, and attachment metadata. Full decoded content is limited to 5 MB. Remote images, styles, fonts, scripts, forms, and tracking resources are never loaded.

`attachment get` requires an explicit message reference and attachment selector. It accepts common documents, PDF, text, and image media up to 20 MB, sanitizes the filename, and only saves the file; it never opens, executes, or extracts it.

## Prepared Draft and sending

- `prepare` reads a Markdown Draft Manifest file, validates account, To/Cc, subject, and optional reply reference, and creates an immutable Prepared Draft. Manifests generated by the skill live under `.mailctl/tmp/`.
- The restricted Markdown renderer supports headings, paragraphs, emphasis, ordered/unordered lists, blockquotes, fenced code, links, and simple tables. It accepts no raw HTML or custom CSS.
- The MIME message contains styled HTML as the primary presentation and a plain-text alternative. The first version adds no signature, Bcc, forwarding, or outbound attachments.
- Reply addresses only the original sender. Reply All is a separate explicit manifest mode and shows every To/Cc recipient. Thread headers are preserved.
- `prepare` writes `.eml`, `preview.html`, and state beneath `.mailctl/drafts/<draft-id>/`. The ID is derived from the exact immutable MIME content.
- `send` accepts only a Prepared Draft ID. The skill must show account, To, Cc, subject, body preview, and ID, then require a separate user instruction of the form `发送 <draft-id>`.
- A Prepared Draft can be sent for 72 hours. Success consumes it. An uncertain SMTP outcome also locks it. Re-sending requires cloning into and previewing a new Prepared Draft. Unsent state is removed after 30 days.
- Read operations may retry twice. SMTP send never retries. A timeout or disconnect whose delivery result cannot be established returns `uncertain`; SMTP does not promise exactly-once delivery.

## Safety

- Mail Content is untrusted data. It cannot change skill instructions, invoke tools, access local files, or authorize a send.
- Reads do not mark messages read, move, label, delete, or otherwise mutate the mailbox.
- Browser automation, POP, Alibaba Mail administrator API, automatic server-Drafts synchronization, and silent backend fallback are excluded.
- Authentication, capability, configuration, permission, input, size, definite-send, and uncertain-send failures are distinct and actionable.
- The skill is explicit-only and scheduled prompts must name `$email` explicitly.

## Test seams

- Package seam: executable validation covers skill structure, explicit-only metadata, bundled CLI, absence of credentials, and installation behavior.
- CLI seam: commands are exercised through their public argument and JSON result interface in temporary Calling Projects.
- External boundary: controlled Keychain, clock, IMAP, and SMTP adapters model success and failure without real credentials or mail traffic.
- Required behavior includes project-bound writes, Git tracking refusal, non-mutating fetches, pagination, size limits, safe HTML, attachment policy, immutable draft IDs, confirmation gating, expiry, consumed/uncertain locking, and no SMTP retry.

## Out of scope

- Creating or initializing the user's real mail project.
- Connecting to a real mailbox or sending a real email during implementation tests.
- Scheduled tasks, event triggers, summary storage, weekly-report recognition/comparison, and Bear integration.
- Mailbox organization, forwarding, Bcc, outbound attachments, aliases, signatures, and multi-account selection.
